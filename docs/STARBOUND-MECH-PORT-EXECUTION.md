## 1. 用户目标与默认决策

必须保持的体验：

- 出生获得召唤器；召唤、接近、上机、驾驶、下机、回收组成完整流程。
- 能看到**当前实际角色**的头部、表情和部分上身，角色坐在机甲中；不是机甲替换角色，也不是贴一个固定头像。
- 首套造型以 **Avian / Champion-00 开放舱**为样板，放弃 v0.2.1 封闭柜体作为默认方向。Champion 升级型是独立候选，不能假定其开放结构和原型相同。
- 左右工具臂可独立使用与替换，能挖通可通行的通道，也能伤害目标游戏中的实际敌人。
- 地面移动、短跳、长按跳跃持续喷气、空中再启动和安全着陆。
- 首版仍不损坏、无限能源。开放舱只是表现，不能因此取消已有的驾驶保护。
- 可以换机体、左臂、右臂、腿、推进器，留有喇叭槽；配置能随当前存档保存与恢复。

默认 G 召唤/回收、F 上下机、左右鼠标对应两臂、跳跃键使用游戏绑定。装配从召唤器的“装配”入口打开；若当前物品交互 API 不支持多动作，先实现可重绑定的装配热键和说明，不能让玩家改 JSON 才能换装。喇叭用独立可配置按键，不能抢占 F。

“移植”不等于第一轮复刻整个 Starbound 世界：太空地图、飞船、任务 NPC、原版种族系统不是前置依赖。目标游戏没有对应环境的内容，做适配或保留为后续项目，不伪造已实现。

## 4. 素材获取、转换与记录

### 4.1 先确认用户素材在哪里

用户提供的是 Wiki 索引 URL，本轮未提供本地 Starbound 素材包路径。接手可以先检查工作区和本机 Steam library manifest 中的 Starbound 安装位置；只读取应用路径与素材，不扫描账号凭据。已有本地安装/解包目录就复用。

推荐素材工作区：`E:\GameArtLibrary\starbound-mechs\`，与既有 Atlas 数据集分开。结构建议：

```text
starbound-mechs/
  source/             # 用户提供/本地提取的原始文件，只读保存
  inventory.json      # 来源与可用文件清单
  converted/          # 转换得到的纹理、帧定义、装配数据
  previews/           # 组装/动画/角色比例对照
  manifest.json       # 哈希、来源、转换规则、版本
```

本地有 `packed.pak` 时优先使用随该安装附带、经核对的 asset_unpacker 工具；先检查实际路径、帮助与参数，输出到新目录。不下载不明解包 EXE，不修改原版包。Wiki 的大图可用于本地参考/选型，但图标、缩略图、整机展示图都不自动等于原生帧表。

若只有 Wiki：取得具体部件页面和原图，记录文件尺寸及用途；缺失动画、锚点或配置时明确登记，使用原创补齐。不能从一张站姿图推断已拥有全部动作。缺素材只阻塞对应内容包，数据结构、目标游戏适配器和测试仍可推进。

### 4.3 转换规则

- 原始图片、JSON/帧表、动画配置和调色映射分开保存；Lua 如用于理解逻辑只做阅读，不能直接在目标游戏执行。
- 写可重复的转换器：读取白名单类型、校验维度和帧边界、输出部件定义与预览。禁止任意脚本求值。
- 统一坐标、角度、pivot、PPU 和像素密度；先确定角色与机体比例再决定 PPU，不把所有文件一律硬缩到 16×16。
- 明确 body 前后层、座位、髋/肩、炮口/钻尖、喷口、遮挡区与碰撞核心。导出为同一份数据供预览和运行时读取，避免重新手抄偏移。
- 保留透明通道、Point/Clamp；先原生尺寸装配再放大检查。颜色替换只映射指定装甲色带，不给脸、眼睛、玻璃和特效统一染色。
- 每张最终贴图记录来源文件/URL、原始哈希、裁剪帧、转换参数、派生哈希、用途和权利说明。

用户提供素材可用于本地开发，但 Wiki 可下载不等于已证明可跨游戏公开再分发。工程允许独立的本地 Starbound 资产包；发布包只包含许可明确的资源或原创替代，素材来源记录随交付保留。此边界不应阻止本地功能实现，也不自动产生公开发布任务。

## 5. 首个可玩版本：可见驾驶员

### 美术验收先行

先制作“真实目标游戏角色坐在 Champion-00 类开放舱中”的侧视装配稿，并与实际洞穴截图比较。需要右/左、静止/行走、平举/上举工具四类基础视图。确认角色脸部可读后再扩到多部件。

角色保持身份、颜色、头部、眼睛、伤痕和实际配件。完整头部与部分上身露出，腿部和座位接缝由低护板遮挡，手放在操纵区域。耳朵/头发可以合理超出边缘，不能直接裁掉。装备真的遮脸时如实显示，不擅自脱头盔。

### 运行时方式

原版 `FacialExpression` 已有独立 head/eyes renderer 和眨眼/状态表情逻辑。先观察实际角色层级、Sprite、material、排序和更新顺序，再设计映射，不按含糊的对象名称猜。

推荐 `PilotVisualProxy`：只创建渲染节点，不克隆 Body、Rigidbody、Collider、Item、Animator 或原生行为脚本。映射实际角色的头部/眼睛/必要上身与服装，在原生视觉更新之后同步；坐姿由展示层处理。真实角色继续由经过验证的驾驶隔离逻辑管理。

- 不用固定假脸，不把主角变成 Starbound 鸟人。
- 状态表情和眨眼分别测试。Body.Update 暂停会冻结部分计时器，必须做窄范围的视觉时间/状态适配，不能为了眨眼恢复整个身体模拟。
- 头朝向与驾驶方向/瞄准协调；停用、死亡、换层、下机和异常时清理代理，恢复之前的渲染/动画/物理状态。
- 遮挡顺序：后侧装甲/座椅 → 角色 → 前护板/近侧操纵杆；武器和喷焰不从脸前扫过。
- 暂停/失焦禁止角色及机体偷偷继续执行控制；输入恢复需要正确释放门禁。

可见性与生理保护是两条逻辑。不要加一个全局 Body 伤害免疫补丁影响其他角色。现有驾驶冻结对症状/计时的行为要记录，暂不顺带改变整套生理平衡。

## 6. 模块系统与装配界面

保留原插件 GUID `local.cu.wayfarermech` 和信标 ID `wayfarer_mech_beacon`，不并行加载另一个同功能驾驶插件。对外名称可以改，存档契约不能随意改。

建议最小组件划分，按职责拆文件即可，不强制多项目：

| 组件 | 职责 |
|---|---|
| MechCatalog / PartDefinition | 带命名空间的部件 ID、槽位、资源引用、锚点、参数与版本 |
| MechLoadout | 当前玩家/本次 run 的组装方案和配色 |
| MechRig / MechVisual | 分层、坐标变换、动画与工具端点 |
| PilotVisualProxy | 真实角色外观映射 |
| MechController | 驾驶状态和物理，不处理所有武器分支 |
| MechArmController | 每侧独立行为、冷却、激活和效果 |
| GameCombatAdapter / MiningAdapter | 目标游戏伤害、命中、掉落 |
| MechSaveAdapter | run 绑定、迁移、安全保存/恢复 |
| AssemblyPanel | 换件预览、可读属性、确认与取消 |

示意定义（字段名是本项目设计，不是已经存在的 API）：

```json
{
  "schemaVersion": 1,
  "id": "wayfarer:champion_open",
  "slot": "body",
  "visual": {"rig": "champion_open.rig.json", "pilotVisible": true},
  "stats": {"mass": 60, "invulnerableByDefault": true},
  "requires": {"rigProtocol": 1}
}
```

外部内容包使用独立命名空间，声明 rig/行为协议版本；缺图、未知槽位、非法数值和重复 ID 在加载时报告并隔离对应内容，不使整个游戏启动失败。只接受已实现行为类型，不将任意 DLL/脚本注入当作“通用扩展”。

装配界面必须有：部件分类、当前槽位、真实预览、与当前配置的属性变化、主/辅色、缺件原因、应用/取消。用户尚未应用的草稿不修改当前驾驶实体。首版只允许回收后或安全停泊下机时换装；应用前验证新碰撞/部署净空。

核心槽位缺失禁止部署并说明；喇叭为空合法。初版完整样板预装，不让新玩家出生后面对空配置。所有生产核心功能在不加载 probe 时仍可使用。

## 7. 运动、碰撞与召唤

把所有输入先转换为语义动作，再由驾驶状态消费。更新循环采样输入，FixedUpdate 做物理；暂停、失焦、菜单、控制台、拖动背包时禁止机甲动作。

状态至少区分：未部署、已部署无人、驾驶地面、驾驶空中、顶碰受阻、退出处理中、场景切换。ThrustRequested、ThrustApplied、Blocked 语义分开；HUD、火焰和音频读取同一份最终状态，不靠“速度小”猜喷气是否开启。

顶碰采用实际接触法线与短距离碰撞体探测；顶角/侧墙/斜面分开，缓存命中需及时失效。避免当前 1.7 世界单位的宽泛探测导致未碰到就熄火。离顶后持续按住应恢复上升，不要求额外重按；仅菜单/失焦等门禁要求重按。

碰撞体由机体定义的核心包围体决定，不包括伸出的武器与喷焰。初期沿用已知 4.2×6.6 作为比较基线，而非所有机体永久尺寸。调整尺寸必须同步净空、召唤、安全退出和钻掘截面测试。

召唤点按“近且玩家可到达、有支撑、净空足够”排序；失败给出原因，不为强制成功清地形。去掉或约束会把机甲投到远处深坑的回退，不把位置差很大的部署当作成功体验。

持续飞行维持当前手感基线，参数由腿/推进器组合决定并有限制；不逐帧累加部件属性。可选零重力控制只在目标世界确有相应模式时启用，不修改全局重力制造测试假象。

## 8. 双臂、采矿与战斗

每侧行为独立，支持交换左/右安装。机械钻、光束钻、实弹是不同执行器，共用目标游戏适配器；不能靠不断追加 `if(partId==...)` 实现整个目录。

采矿保留原生方块伤害、硬度、掉落及保护区域。刷形按当前 hull 的投影加净空余量计算；限候选、限处理、限粒子/音频，低帧率不积压补发。机械钻的接触距离与表现一致，光束钻可更远，避免拿机械钻打十几米外的墙而无可见连接。

攻击源必须是实际工具轴线与端点；目标在端点后方时不能把射线反向穿过机体。炮口已进入墙内时先检查肩座到炮口的遮挡，命中最近阻挡而不是从墙后开火。瞄准角限制、后坐和动画不能让画面朝一个方向、伤害朝另一个方向。

战斗必须核对目标游戏的 Body/Limb 与 BuildingEntity/animal 类型及其原生受伤 API；保留敌人的受击、死亡和掉落流程。明确过滤本机、驾驶者、友方、无敌/不可攻击实体。**不能继续统一 ignoreBody=true，也不能改成 false 后不做自身伤害检查。**

最小证据：同一已知目标受击前后的生命/伤害事件，玩家正常开火后发生变化；炮火只破墙不算战斗通过。角色与动物两类至少各测一次；友军和自身各测一次不会误伤。地形伤害、动物伤害、身体伤害分别调参。

## 9. 保存、退出与兼容迁移

装配配置属于具体角色/run，不能只写全局 BepInEx cfg 导致两个存档互相覆盖。配置文件只放默认调参、输入和模式。

设计 `schemaVersion`、loadout 部件 ID、配色、模式、资产包版本及必要驾驶恢复状态。优先使用当前 CUCoreLib 已验证的随原版存档 provider；必须核对实际 DLL/API，不把文档设计当成已有调用。

缺部件包时使用明确的保底套装并提示；保留原始未知 ID 以便资源恢复，不静默永久抹掉。旧版只有信标没有 loadout 时迁移为预装 Champion-00 样板，信标不重复发放。未知较新 schema 不覆盖原记录。

默认仍“保存时回收、读档后重新召唤”，但保存前必须证明驾驶员处在可站立的安全点：附近点 → 本场景最近安全点（重新检查是否被挖空）→ 有界搜索。不能把找不到点的 `unsafe-current` 继续作为成功路径。

**无安全点的明确回退设计**：随同一次原版保存记录最小驾驶恢复快照（机体配置、当时驾驶标志、场景身份/位置及安全状态），进入原版保存阶段时不让裸玩家落地模拟；读档后在世界与角色 ready、普通控制开放之前恢复保护和机甲/座位。如果目标游戏读档会重建世界、场景坐标不匹配，必须先在新场景验证可部署点，不能使用旧世界坐标直接生成。恢复完成后再解除等待状态。恢复失败给出可诊断信息并保持安全受控状态，不能让角色隐身锁死或直接坠落。

上面需要真实探明原版保存/读档顺序；若当前 API 无法提供可靠切入点，此路径记 BLOCKED 并解决 hook，不伪称兼容。同步 SaveGame Prefix 中不能等待多秒降落，不能取消原版保存且不提示，也不能只写一个不同步的任意 sidecar 冒充可靠持久化。

正常下机可在无落点时拒绝并提示。死亡、失去意识、换层、退出主菜单、卸载等强制路径各自定义并测试；所有情况下正确清理代理、相机和输入接管。按自己的 Harmony ID 卸载，不全局 UnpatchAll。

## 10. 可选能源模式与后续内容

首版 creative 为默认：无限能源、不损坏，不因燃料为零强制踢人。装配 UI 中隐藏不适用属性或标为不限，不能显示假消耗条。

后续 survival 模式可引入能量池、被动消耗、受击消耗、补给与环境适配，但须另做安全弹出/损毁测试。能量到零的行为不能违背驾驶员安全策略，尤其不能把上一个模式的无损约定偷偷改掉。不要把原版能源数值照搬到不同重力和伤害尺度的游戏。

蓝图/制作阶段映射到目标游戏实际材料和制作入口，初始赠送方案继续可用；不强制创建 Starbound 的任务 NPC/飞船才能使用。更多机体/工具作为数据包加入，新增行为类型才需要代码修改。零重力和多人排到独立里程碑，未实现不出现在已支持列表。

## 11. 里程碑、工程量与完成判据

以下为工程估计，不是交付承诺；素材完整度和原生角色渲染兼容是主要不确定项。

| 阶段 | 可审查产物 | 完成判据 | 估计 |
|---|---|---|---|
| M0 环境/素材清点 | 指纹、回退、素材 manifest、标题阻塞诊断 | 目标最小组合可进入世界，或明确隔离阻塞原因 | 半天–1 天 |
| M1 开放舱样板 | Champion-00 风格机体与 PilotVisualProxy | 真实主角可见、眨眼可见、上下机恢复、基本驾驶 | 1–3 天 |
| M2 模块化与双臂 | 目录、换装 UI、两种机体/腿/推进器、三种臂行为 | 同一运行中通过玩家入口换件并观察差异，双臂可交换 | 2–4 天 |
| M3 战斗/安全闭环 | combat/save 适配、顶碰修复、存档迁移 | 真敌人受伤，自身过滤，高空/无安全点保存重启通过 | 2–4 天 |
| M4 内容扩展 | 更多部件、配色、制作/蓝图 | 声明的每种行为至少一条真实入口验收 | 按数量追加 |
| M5 可选高级模式 | 能源/损毁、环境、零重力、多人 | 各有独立测试矩阵 | 独立估算 |

M0–M3 合计约 **一到两周集中开发**，完整大量部件复刻会更长。M1 是最早应让用户看到的结果，不能先花数天建大框架却仍没有可见主角。

正常情况下按阶段自主推进。若准备做一套与参考明显不同的美术造型，先给带主角的对照图，避免再次把未经审美检查的程序化矩形资产称为最终美术。

## 12. 实机自动化与测试矩阵

测试仍用隔离副本、独立 userdata、实际键鼠入口；fixture 只布景或准备材料，不能直接设置 piloting=true、血量变低或位置上升来冒充玩法成功。

现有工具：`tools/cumod.py`、`tools/launch_mech_test.ps1`、`tools/MechProbe`、`tools/TestIsolation`。启动脚本不负责完整沙盒创建；现有 probe 也不是通用自动动作服务。先核对其能力再用。

已有 `runs/v021-visual2` 与 `runs/v021-baseline` 的新旧版本均停在无按钮标题背景。不能重复盲点菜单。先检查旧版、最小依赖、输入焦点、实际路径和日志，将环境/库/机甲回归分开归因；必要时重建一个新隔离副本。不要更改正式存档来修测试环境。

自动化提效：一轮进程内完成外观、换装、攻击、移动、切场景矩阵；只在 DLL 变更、启动组合或重启读档验证时重启。按可观测条件等待，不固定睡几十秒就判 PASS。若 UI 工具不能长按，换有文档支持的输入接口或保留人工录制验收，不能用短按证明持续飞行。

| 用例 | 必须看到的结果 |
|---|---|
| 出生/旧存档入口 | 一份有效召唤器、预装完整配置，旧信标无重复 |
| 开放舱与身份 | 两种可用角色外观、左右朝向，脸/配件与原角色一致 |
| 眨眼与表情 | 录像中有自然眨眼；受控状态变化确实改变表情，分别记录 |
| 上下机恢复 | 原 renderer、collider、rb、动画、相机和控制恢复，反复 10 次无残影 |
| 换装 | 正常界面应用/取消、缺核心部件、无喇叭、换机体和左右臂交换 |
| 身体尺寸 | 新机体召唤净空正确；能走入自身挖出的水平/向上/斜向通道 |
| 喷气 | 短按/长按/空中再按/松开/失焦/暂停；不以同一结果代替全部 |
| 顶碰 | 平顶、顶角、斜面、侧墙；持续按住横移离顶恢复上升，HUD/火焰同步 |
| 工具一致 | 左右、上下、近距离、炮口入墙；端点和伤害方向一致，无穿墙起射 |
| 战斗 | Body/Limb、动物、建筑实际受伤；自身和驾驶员不误伤，友方策略明确 |
| 挖掘与掉落 | 软/硬块耗时、原生掉落、保护边界、双臂同时触发预算 |
| 存读档 | 地面、高空、缓存点已挖空、缺部件包、原版读档重建世界、旧信标迁移 |
| 生命周期 | 换层、死亡/失去意识、回菜单、再次进入，无残留实体/回调 |
| 性能 | 同场景预热后 60 秒 p50/p95 与样本数；30/60/高帧率运动对照 |
| 无测试插件 | 移除 probe 后正常召唤、换装、驾驶、表情、攻击 smoke |
| 多人/其它 Mod | 没有实测即 NOT_RUN，不因库支持而推断支持 |

保存每轮输入指纹、DLL/资源包哈希、过程日志、截图/录像、状态快照和明确断言。Probe 新增 loadout、槽位/行为、驾驶员代理映射状态、瞄准轴/端点、当前驾驶状态、保存恢复阶段，观测字段不得承担生产逻辑。

有限测试只证明有限场景。不要把“程序集加载”写成“真实游玩通过”，不要沿用旧 DLL 的截图给新版本作证。

## 13. 交付物与最后检查

- 版本化 Mod-only 包；核心代码与外部资源包分开，依赖明确。
- 源码、转换器、资产 manifest、原创/本地导入来源说明。
- 有实际主角的截图/短录像：左右静止、行走、喷气、钻探、战斗、装配换件。
- 操作说明、模式默认值、支持的具体部件与缺失项。
- schema/迁移规则、旧版回退包、配置与资产版本策略。
- 独立 profile lock → stage → verify；测试 DLL/资源哈希与交付一致。
- 报告 STATIC、BUILD、STAGE、BOOT、PLAYER_VISUAL、GAMEPLAY、SAVE_RELOAD、PERFORMANCE、COMPATIBILITY 各层结果与证据。未执行写 NOT_RUN，基础设施阻塞写 BLOCKED。
- 确认玩家包不含 probe、布景脚本、隔离修改程序集、原版游戏 DLL、用户存档和未确认可分发的素材。

M0–M3 通过才称为“可见驾驶员的模块化机甲核心移植完成”。只有 M1 完成时，应称“开放舱样板”，不能包装成 Starbound 全机甲系统已移植。
