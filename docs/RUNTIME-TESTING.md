# Agent 真实游玩验收

此文是执行规范，不是已经运行的自动化服务。本次没有安装 loader、启动游戏或改动任何存档。现有 RimBridge 是另一游戏的工具，不能用于这里。

## 1. 三种能力等级

| 等级 | 方法 | 可以证明什么 |
|---|---|---|
| L0 | 构建、静态扫描、profile/stage 校验 | 文件和构建层通过；不能证明游戏可运行 |
| L1 | UI agent/人工操作真实游戏 + 截图/录像 + 本轮日志 | 实际玩家流程可用，视觉正常；量化数据未必精确 |
| L2 | L1 + 独立测试插件输出状态、有限动作接口 | 精确验证注册、状态变化、耗电、保存恢复；仍需 L1 验证输入和 UI 路径 |

当前工具包提供 L0 工具和 L1/L2 规范。可用的电脑控制工具可以执行 L1；先按其使用规则读取界面。没有接入电脑控制时，不编造已点击、已进入游戏或截图。L2 需要针对当前游戏程序集实现测试插件，不能把这里的接口草案当作现有 API。

## 2. 隔离是前置条件

已观察到游戏的 save/settings/console 使用 Unity `Application.persistentDataPath`，本机基线位于 `%USERPROFILE%/AppData/LocalLow/Orsoniks/CasualtiesUnknown`。Windows 上该目录与用户/厂商/产品名关联，复制游戏目录不会自然换存档路径。依据见 [Unity 文档](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Application-persistentDataPath.html)。

推荐顺序：

1. **独立 Windows 测试用户/VM，独立游戏副本与用户数据。** 在该用户内确认实际 persistentDataPath；核对 Steam Cloud/自动同步设置，不把独立 Windows 用户等同于独立云存档。受游戏许可和 Steam 启动行为影响的部分需实际确认。
2. **已验证的测试专用数据重定向。** 若后续做 bootstrap，必须在首次读写设置/存档前生效；不能只 patch SaveGame 而漏掉 TryLoadGame、设置、console、第三方库路径。用文件访问观察证明实际写入测试目录，正式目录前后哈希不变。不得套用 RimWorld 的 `-savedatafolder` 或假设 Unity 有通用同名开关。
3. **维护窗口内备份/还原原用户数据**仅是最后手段：游戏和同步退出、完整备份、记录哈希、不与用户同时游玩、结束后核对漂移。任何并发变化先保留双方副本，不盲目还原覆盖。

前两种未就绪且用户未选择第三种时，实机测试为 BLOCKED：storage-isolation。可以继续 L0、编写测试插件和案例。用户请求编写流程不自动授权修改系统账号、同步设置或正式存档。

每轮前置记录：运行 ID、PID、实际 exe 路径、游戏 fingerprint、加载 Mod GUID/版本、profile lock 哈希、用户数据实际路径、测试 save 来源及哈希、输入映射、分辨率、语言、开始时间。不同测试进程不得共享同一个存档目录。

## 3. 执行状态机

```text
PRECHECK → STAGED → ISOLATION_VERIFIED → LAUNCHED → MENU_READY
 → WORLD_READY → EXERCISED → SAVED → CLEAN_EXIT
 → RELAUNCHED → RELOADED → ASSERTED → EVIDENCE_SAVED → COMPLETE
```

每个状态有可观察条件和超时。建议启动/加载 120 秒、单动作 15 秒；慢机器可按基线调整并记录。靠条件轮询，不靠固定 sleep 就宣称 ready；UI 可观察、状态快照或日志事件均可作为条件。超时只重试一次恢复（关闭可见弹窗/重新采集状态），重复失败就输出具体失败层；不要无限按键或重启用户游戏。

启动新进程只控制自己记录的 PID。不要杀掉所有同名游戏进程。正常退出失败时保留日志，只有测试环境和该 PID 确认后才考虑强制结束。

### 核心 E2E（每个行为 Mod 都需覆盖）

1. 原版或必要库基线启动：进入菜单→新建测试 run→可移动，记录同场景日志基线。
2. 目标组合启动：核对实际加载 GUID/版本/哈希与计划一致；进入世界，不出现新增加载错误。
3. **玩家入口**：打开真实物品/制作/设置界面，通过正常入口触发功能。资源可由 fixture 提供，但实际制作/穿戴/使用必须走 UI 或与玩家相同的游戏命令入口，不直接给字段赋“正确结果”。
4. 读取状态变化，捕获能看见对应场景的截图。日志、状态、视觉一起判断；仅日志写了成功不算真实交互通过。
5. 验证异常条件：资源不足/空电/无目标/错误场景/卸下装备；不能卡死或刷屏。
6. 经正常保存入口保存，确认写入完成且文件时间/哈希变化；退出整个游戏进程。
7. 启动同一锁定组合，正常读档；检查 ID、数量、耐久、电量、装备状态和自定义持久状态。随机字段和运行时临时 cooldown 按声明规则断言，不强求整个存档字节相同。
8. 再次切场景/切语言/返回菜单重入，核对注册和订阅没有重复。
9. 本轮日志与基线比对，对新增异常逐条归因；拍摄最终画面，退出测试实例或暂停并说明。

Debug spawn 适合 fixture 和快速 smoke，但不证明制造入口、材料扣除、配方可见性、交互提示正常。使用作弊命令还可能改变成就状态；测试环境单独记录，不把成就验证混入这一轮。

## 4. 按 Mod 类型选测试，不强制全套

| 类型 | 最小真实路径 | 高风险边界 |
|---|---|---|
| 物品/配方 | 获取材料→制作→放入背包→使用→存读档 | 缺材料、负重、容器嵌套、ID 冲突 |
| 穿戴/武器 | 穿戴/手持→移动/攻击→卸下 | 槽位冲突、NPC、左右朝向、跳跃/攀爬、空电、耐久 |
| 液体/状态 | 获取→饮用/注射/应用→观察生理变化 | 剂量边界、重复施加、死亡/重生、存读档 |
| 世界/战利品 | 正常新建世界→探索→交互 | 旧存档、新层/重进场景、概率需统计而非单次断言 |
| UI/汉化 | 目标菜单→切语言→交互 | 长文本、占位符、缩放、missing key、语言切换重载 |
| 音频/视觉 | 真实触发→录音/截图 | 音量、重复播放、帧率、层级/遮挡、资源释放 |
| Harmony/QoL | 原版基线→相同行为→目标效果 | 缺失方法、其它补丁同方法、主菜单无 player |
| 存档扩展 | 写入自定义状态→完整重启→恢复 | 旧 schema、缺字段、迁移失败保留原档、禁用 Mod |

性能用同一 fixture/场景/机器，记录 baseline 和 candidate 的帧时间及分配。预热后采样至少 60 秒，报告 p50/p95 与样本数；预算按功能设定，不能凭单张 FPS 图宣布性能正常。

## 5. Titan 的首轮验收用例

这些是根据当前代码给出的预期，尚未实机证明：

- 注册 4 个自定义物品和 4 条配方，第二次进世界仍是 4，不重复。先从源码读取实际 ID，不猜测名字。
- 用 UI 制作护甲板和外骨骼，核对材料消耗与结果数量；debug spawn 另列 smoke。
- 三种角色外观（当前项目资料指向 charType 分支，实际可选项以游戏为准）中检查头盔/外骨骼的肢体对齐、移动、左右朝向、蹲伏/跳跃、前后层级。美术合格需人工或视觉检查，不靠文件存在。
- 穿戴且有电时，60 秒**游戏活动时间**的被动消耗约 12 charge units（当前 0.2/s），不是 12% 电量；读取量纲和实际最大电量后换算，容差由采样帧时间确定。
- 在满足站立/非攀爬/冷却条件时跳跃，额外消耗约 12 units，加上采样间隔被动耗电。与无装备基线比较速度/高度；直接调用 boost 方法不能替代按跳跃键。
- 电量低于跳跃费用时无加速，电量为空时提示不连续刷屏；卸下后不再被动耗电。验证无电时护甲仍按当前设计生效，除非产品简报另有要求。
- NPC 穿戴时玩家按键不得意外驱动 NPC；菜单/输入框打开时不得意外触发。当前 Update 使用 Input.GetKeyDown，这两条必须实测。
- 受击检查覆盖肢体的实际伤害与耐久，使用同伤害源和相同基线，随机性受控；不从 tooltip 直接推断减伤。
- 保存含装备、电量、货舱内容的 run→退出进程→读档→再次使用。明确 cooldown 等状态是否需要持久化。

## 6. L2 测试桥契约（待实现）

先以 CUCoreLib 控制台命令 + JSONL 日志做最小实现，足够再考虑 localhost IPC。独立测试插件 GUID，例如 `dev.local.cu.testbridge`；只进入测试 profile，不打进玩家包。API 名称以下为设计，不是库已有方法。

```json
{"protocol":1,"runId":"run-001","requestId":"r7","op":"snapshot","args":{"scope":"player"}}
```

```json
{"protocol":1,"runId":"run-001","requestId":"r7","ok":true,"frame":830,"gameTime":41.5,"data":{"scene":"world","ready":true},"error":null}
```

最小能力：`hello/capabilities`（协议/构建/加载插件/真实数据路径）、`snapshot`（注册表、玩家、物品实例、暂停/输入状态）、`fixture`（测试世界内准备材料）、`invoke`（白名单游戏操作）、`save`、`events_since`。稳定实例 ID 不能只用屏幕坐标。状态快照用 DTO，不序列化整个 Unity 对象图。

实现约束：

- Unity 对象访问排队到主线程；每帧限量执行，队列有界、每请求超时；读状态与等待加载不死锁主线程。
- 有副作用请求用 requestId 去重；超时后查询原结果，不盲目重发一次制造/购买/保存。跨进程重启生成新 runId。
- 如使用 IPC，仅绑定 loopback，会话凭据临时存储，不写源码/交付日志；禁用任意 C# eval、任意路径写入和任意 shell。
- 真实输入测试通过 UI agent 发送按键/点击；bridge 只能提供观测和 fixture。直接方法调用测试单列为集成测试。
- handler 返回 ok 只表示请求处理成功，runner 仍需等待结果状态和断言；比如 save 接受成功后仍确认文件写完。
- 测试桥自身先验收：heartbeat、加载场景、错误请求、超时、去重、主线程调度、数据路径、正常退出。桥失败分类为 INFRA_ERROR，不能把 Mod 判 PASS 或直接判 Mod bug。

## 7. 证据与失败归因

每轮目录至少：`environment.json`、`profile.lock.json`、`steps.jsonl`、`results.json`、`logs/`、`screenshots/`、存档副本与其 hash（只留本地）。固定 seed/fixture 有则记录，无则明确不可完全复现。

步骤结果至少：caseId、动作类型（UI/fixture/direct）、开始结束时间、precondition、expected、observed、status、evidence 相对路径。PASS 必须有观测与证据；截图路径存在并不表示内容已经检查。

日志按本次 PID/会话/时间截取，保留原始日志和分类结果。旧日志出现 Error 不直接归罪本 Mod；新异常也不能因为堆栈没有本 Mod 名字而忽略。对失败最小组合复现，分类为 ENVIRONMENT / LOADER / DEPENDENCY / REGISTRATION / GAMEPLAY / SAVE / VISUAL / INFRA_ERROR。

先修最早的因果错误，再重新启动和重跑受影响用例。修复代码后的证据必须对应新 DLL 哈希。发布前再做一轮不含测试桥的正常加载和核心玩法 smoke。
